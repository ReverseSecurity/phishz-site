How it works

Detection is one stage of five

A filter owns the moment of delivery. The weeks before it, and the months after, are where breaches actually happen, and where a small team is usually on its own. Step through all five.

Someone is building the trap

A domain is registered to look like yours: a swapped letter, a lookalike character, a different ending. Mail gets switched on. Somebody tests whether they can send as you. All of it visible, all of it before a single message lands.

The engine

An AI engine we built, trained and run on your own hardware

Not a model on its own. A cascade of purpose-trained models wired into custom inference loops, with detonation, optical reading and sender-authentication signals fused into a single verdict. Engineered to run on an ordinary server CPU: no GPU, no accelerator, no cloud, no API key.

1

The quick read

Every message · milliseconds · CPU

A small, fast transformer trained purely on phishing language sees everything first. Most mail is settled here and nobody is interrupted.

Quantised to integer weights and compiled for CPU inference, so a verdict costs milliseconds on an ordinary core. Confidence thresholds are tunable at runtime without redeploying.
2

The careful read

Anything uncertain · still CPU

Uncertainty escalates itself to a far larger model before anyone is told they have been attacked. The cascade decides when that is worth the compute.

The escalation loop is ours: a margin test on the first stage routes only genuinely ambiguous mail onward, which is what keeps a large model affordable without an accelerator. Pinned to a fixed revision, so the engine cannot change underneath you.
3

Specialists

Optional · off by default

A text message and a long email do not read alike. Add a trained specialist per shape and let the ensemble weigh them.

Additional classifier heads routed by message shape, their opinions blended into the ensemble at a weight you set, with the fusion logic and every stage score exposed rather than hidden.
No GPU

Security AI usually means renting somebody else's accelerators and posting your mail to them. This cascade was engineered to fit a plain virtual machine. Quantised weights, batched CPU inference and a routing loop that spends the big model only where it changes the answer.The appliance runs on ordinary vCPU and RAM, with no CUDA, no accelerator passthrough and no per-token bill. Adding a specialist model is a download, not a hardware project.

Trust

It holds the keys to your email

That makes it a target, and it's built on that assumption.

No door inwards

Internet-facing parts live on separate machines. The appliance only ever calls out.

Edge nodes are never called inbound. The appliance dials out over a mutually authenticated tunnel and polls for work.
Secrets in a vault

Every credential, token and certificate lives in a sealed HashiCorp Vault. Never in a config file, never in an environment variable, never on disk in the clear.

The vault re-seals itself on every reboot and a person has to unlock it, so a stolen disk image or a cold backup gives up nothing. Services hold no long-lived secrets of their own; they draw what they need at runtime and nothing else.
Hardened from the kernel up

A locked-down Linux base where every service runs without privileges, is walled off from the others, and cannot gain new rights once it is running.

Containers run rootless with capabilities dropped, privilege escalation blocked, read-only filesystems wherever the service allows it, and a mandatory access-control profile per service. Fifteen services across three network segments, one of which has no route to the internet at all.
Everything attributable

Roles gate who can delete or release. Every action is recorded against a name.
